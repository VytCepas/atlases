The story in one page

the question, the four hypotheses, what was built, what it found

Do Russian and Belarusian outlets give the Baltics more attention and a harsher tone than everyone else, and can a system watch that live? You answered it with GDELT metadata, a Lambda architecture on Google Cloud and four hypotheses whose pass/fail rules were written before the tests ran.

The question, in plain words

Since 2022 the Baltic states have suspended or banned Russian and Belarusian broadcasters, and disinformation researchers (EUvsDisinfo, DFRLab) document individual campaigns. Those are case studies. What was missing is a continuous, measured view: how much attention Russian and Belarusian outlets give Lithuania, Latvia and Estonia compared with everyone else, in what tone, and whether a spike in coverage can be seen as it happens.

So the project has two halves that the coursework both needs: an analysis (a month of history, September 2026, with confidence intervals) and a live system (from 1 October, a new file every 15 minutes, a spike detector). That pair is exactly what a Lambda architecture is for: a batch layer for history and a speed layer for now.

The data

GDELT GKG 2.1, two feeds, 15-minute slots, five groups, one parser

Every 15 minutes GDELT publishes one zip per feed describing every news article it indexed. article.parse turns each row into four facts the whole project needs: who published it (group), is it about the Baltics, is it about security, and its tone.

Two feeds, one file per slot

GDELT's Global Knowledge Graph 2.1 is metadata, not text: for every article it lists the source, places, people, organisations, themes, tone and headline. There are two feeds. The English feed holds articles written in English; the translated feed holds articles in about 65 other languages, machine-translated into English before GDELT tags them. Russian-language outlets such as ria.ru live in the translated feed.

A slot is a 15-minute window, named by its start time as a 14-character UTC string YYYYMMDDHHMMSS. That string is the key of the whole pipeline: the Kafka message key, the raw file name, the monitor's slot and Spark's 15-minute series. A day has 96 slots, so September is 30 × 96 × 2 = 5,760 zips (0 missing, 35.6 GiB, 9.08 M articles).

The slot string sorts in time order as plain text, so gdelt.slots(first, last), gdelt.shift(ts, n) and a simple ts <= last_closed comparison are all the time logic the pipeline needs. The producer walks slots oldest first and the monitor closes them in the same order (05 Speed layer).

TrapThe download URL is storage.googleapis.com/data.gdeltproject.org/…, not data.gdeltproject.org. The latter answered a not-yet-uploaded file with a 404 that Google's edge cached for an hour (cache-control: public, max-age=3600), so every translated file arrived about an hour late and three slots were wrongly marked missing. Fixed in commit bb3e277 (10 GCP & operations).

From one row to one Article

A GKG row has 27 tab-separated columns, several of them nested lists (; between items, , or # inside an item). article.parse reads only the columns it needs and returns a small typed record, Article, which is what every layer passes around: the Kafka message body, the Spark row, the AI input.

Three details matter in the defence. Locations are read from the V2 field and fall back to V1; each location is type#name#COUNTRY#…, and the third field is a FIPS country code, so Lithuania is LH, Latvia LG, Estonia EN (not ISO's LT/LV/EE). Themes come from the V2 themes column, whose items look like MILITARY,1626 (a theme and a character offset): the code keeps the part before the comma. Language comes from the srclc: tag in column 25; the English feed has none, so it defaults to eng.

Five groups: how a domain is classified

The constants above the function hold the lists: RU_BY_DOMAINS (rt.com, tass.com, ura.news, ruptly.tv), RU_BY_PREFIXES (sputnik, baltnews, rubaltic), and SECURITY_THEMES: MILITARY, ARMEDCONFLICT, WMD, BORDER, ALLIANCE, MARITIME_INCIDENT, TERROR, CYBER_ATTACK, TAX_FNCACT_TROOPS, SECURITY_SERVICES, plus any theme starting with TAX_WEAPONS_.

Traprt.com is matched as a whole domain, not a substring: travelmarketreport.com contains "rt.com" and is correctly other (a test case in test_article.py::test_group). And sputniknews.com is ru_by by its prefix even though it ends in .com.

article.py is pure (no I/O), and every layer imports it: the producer parses with it before Kafka, Spark's mapper.map_file parses with it, and the baseline Pool uses the same mapper. So the speed and batch layers classify T648 identically, and the stream = batch check (09 Correctness) can compare their counts slot for slot.

Quick check

The same headline from rus.delfi.lv, with srclc:rus: which group?

Answer

baltic_rus: the Baltic TLD test runs first, then the Russian-language test splits Baltic outlets. That group is H2a's second reference: Baltic outlets writing in Russian.

Tone is GDELT's dictionary measure: the percentage of positive words minus the percentage of negative words. A difference between groups is therefore in "tone points", never a ratio. It is a crude instrument (dictionary-based, and applied after machine translation for the tr feed), which is exactly why H2a compares ru_by mainly with other translated outlets.

  1. Why does the Baltic-domain test run before the Russia/Belarus test in group()?

    Because a Baltic outlet can write in Russian (rus.delfi.lv). Testing the Baltic TLD first guarantees it is classed as baltic or baltic_rus, never ru_by. That keeps baltic_rus clean as H2a's second reference group: Baltic outlets in the same language as ru_by.

    Tone is counted from English words. ru_by articles are mostly machine-translated first, and translation changes word choice. Comparing translated with translated means both sides pass through the same noisy step, so a difference is less likely to be an artefact of translation.

Architecture

Lambda: batch, speed and serving layers · why not Kappa · what runs where on GCP

History goes through a batch layer (raw zips in a bucket → Spark → Parquet), the live window through a speed layer (producer → Kafka → monitor), and a serving layer (report.py) reads both. Kappa was rejected because it would put 30 days of history into one unreplicated broker.

Lambda, mapped onto your code

The Lambda architecture (Marz & Warren) splits a data system into three layers. The batch layer keeps an immutable master dataset and recomputes views from it: slow, complete, correct. The speed layer processes only recent data as it arrives: fast, incremental. The serving layer answers questions by reading the views. Your system has all three, and one extra box Lambda does not demand but you added: a check that the two paths agree.

T648 belongs to 30 September, so it never touched Kafka: mirror downloaded its zip into raw/ and Spark turned it into a silver row. Its live twin, the same kind of row in a slot after 1 October 00:00 UTC, takes the lower path: the producer sends it to Kafka, the monitor counts it in its slot, and the producer archives the zip into the same raw/ tree. On every boot Spark re-reads those archived zips into lake-live/, and stream = batch checks that both paths counted it the same way.

Lambda's known price is two code paths that can drift apart (Kreps, "Questioning the Lambda architecture"). You pay it in two ways: both paths call the same article.parse, and checks.stream_vs_batch compares every slot the monitor closed with Spark's series_15m over the same files. That check found the id reuse (09 Correctness).

TrapIn textbook Lambda the speed layer is allowed to be approximate and is later overwritten by the batch layer. Here it is not overwritten: the monitor's slots are the live output, and they are checked against batch instead. The 11 incident slots of 2 October stay wrong in the stream, and you report them.

Why not Kappa?

Kappa (Kreps) keeps one replayable log and runs one stream job; to recompute, you replay the log. It removes the second code path. The question is where the history lives.

  1. Kappa's requirement: the log must hold everything you may ever want to recompute. For you: 30 days, 35.6 GiB of compressed raw files, more once parsed into JSON messages.
  2. Your constraint: one broker on one VM, so every topic has a single copy (the compose file even sets KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1), and a student budget. That log would be the only copy of history.
  3. Lambda instead: history lives in raw/ in the bucket; Kafka keeps 14 days (KAFKA_LOG_RETENTION_HOURS: 336), enough for a stopped consumer to catch up.
  4. The price: two code paths. Paid by sharing one parser and checking stream = batch on every boot (vm.sh step 7).
  5. Future: FW1 publishes parsed events to one replayable, replicated log; then there is nothing left to reconcile.

Lambda's master dataset is what makes "a failure costs time, never data" possible at the system level: if Kafka, the VM or the lake is lost, everything rebuilds from raw/ in the bucket plus the code tarball (up.sh + vm.sh). The producer's archive-after-ack rule (05 Speed layer) is the same idea at the level of one file.

What runs where on Google Cloud

The VM runs one image for every pipeline step (Dockerfile: Python 3.12, a Java runtime for Spark, the locked dependencies, an unprivileged user, entry point baltic <command>). Compose starts Kafka, the producer and the monitor as long-running services (restart: unless-stopped) and runs every other step as a one-off job container. The model has its own image, with the weights baked in so a cold start only loads from disk.

Trap"Spark is a cluster tool, so where is the cluster?" There is none: Spark runs in local mode, one JVM with n worker threads on the VM. That is vertical scaling, and the scaling study shows its limit (06 Batch layer). Dataproc was not possible: enabling its API is a project-wide change in a shared project.

Speed layer

producer → Kafka (one partition) → monitor → slots and alerts, plus the warm start

The producer publishes every new GDELT file to Kafka in time order and archives it only after Kafka confirmed it; the monitor closes each 15-minute slot once, oldest first, when both feeds are done and every announced article has arrived, then commits its offset only when nothing is half-read. Delivery is at-least-once; duplicates die on the (id, url) key.

The producer: one poll, slot by slot

The producer runs Ingestor.run(): every 60 seconds it calls poll(), and a failed poll is logged and retried, because a long-running service must not die on a network hiccup. One poll reads both index files, then walks every slot from since to GDELT's newest, oldest first, both feeds per slot. Its only state is the archive on disk: a file whose zip or .missing marker exists is settled and skipped.

Four rules hide in those 25 lines. Learn each with the reason:

  • Slot-outer, feed-inner loop. for ts … for feed … sends slot 09:00 of both feeds before slot 09:15 of either. The first version had the loops the other way round and sent the whole English backlog before any translated file (the "N1 bug"); a mutation swaps them back and test_catch_up_publishes_slot_by_slot_both_feeds_each must go red.
  • A lagging feed does not block the other. if ts > newest[feed] skips a slot that feed has not listed yet, so English keeps flowing while translated is behind (test_a_lagging_feed_does_not_block_the_other).
  • The 404 grace rule. GRACE_SLOTS = 96: a 404 for a slot less than a day older than the feed's newest means "not there yet" (late upload, a CDN, throttling). The pass stops and waits. Only a 404 at least a day old is accepted as "GDELT skipped this file": the producer publishes it with zero articles (so the monitor still gets its done marker) and writes TS.missing.
  • since is fixed once. Without --since the first poll starts 8 slots (2 hours) before GDELT's newest file, and keeps that start: a sliding window would let a slot that is still waiting slide out of view and be skipped forever.

The 404 rule is the clearest case of "time, never data, never silently": skipping too early loses data silently, waiting shows up as lag. It paid off on 1–2 October: data.gdeltproject.org served a cached 404 for an hour, every translated file arrived about an hour late, and the damage was visible lag (and 11 incident slots in stream = batch), not silent loss. Fix: the storage endpoint, commit bb3e277 (10 GCP & operations).

Archive after ack: why the order of two lines matters

publish sends one message per article, then a done marker {"kind": "done", "slot", "feed", "ids": distinct keys sent, "sent_at"}, then flush(120) blocks until the broker has acknowledged everything. If a message is still unacknowledged after the flush, or any delivery callback reported an error, it raises. Only when publish returns does poll write the zip into raw/.

  1. Crash before the archive: the zip is not on disk, so the next poll sees the file as unsettled and publishes it again. Some messages may now be in Kafka twice: at-least-once, and the monitor's key set absorbs them.
  2. Archive before publishing (the mutation): a crash between the two would leave a zip on disk whose messages never reached Kafka. The next poll would skip it as settled: silent loss. test_a_file_is_archived_only_after_the_sink_confirmed_it catches that order.
  3. One bad send fails one file: self.failed = 0 at the start of each publish counts only this file's failures, so a broker hiccup does not poison every later file.
  4. A full local queue waits: on BufferError the producer polls for 0.5 s to let the queue drain, then retries; it never drops the message.

Time order is built in three places on this tab: the producer's slot-outer loop, Kafka's single partition (order is guaranteed only inside a partition), and the monitor's oldest = min(self.open). Remove any one and the close rule breaks. The slot string itself is defined in 02 The data.

Kafka, as configured

Why one partition? Kafka guarantees order only within a partition. The monitor's close rule needs the global order the producer published in (slot 09:00 before 09:15). With several partitions, messages of different slots could interleave arbitrarily. One partition costs parallelism, but the load is about 4 messages per second on average, which a single partition carries easily. just up creates the topic explicitly with --partitions 1, and KAFKA_NUM_PARTITIONS: 1 sets the broker default as well.

acks=all + idempotence: the broker acknowledges a message only when it is fully written, and the idempotent producer attaches sequence numbers so a message the client retries is not written twice. Together with archive-after-ack that gives "never lost". It does not give "never duplicated" across a producer restart: a re-published file is a new send, so duplicates are possible and handled downstream.

One partition, one broker, 14 days: the smallest Kafka that carries ~4 msg/s and lets a stopped consumer catch up. The managed alternatives (Pub/Sub ≈ $0, Managed Kafka ≈ $41 for 6 days) are FW4; the trade-offs are in 03 Architecture.

The monitor: assembling and closing slots

Slot.add does one of two things. A done marker records the producer's send time and how many distinct articles that feed announced. An article is counted only if its key (id, url) is new for that feed: then about rises by 1 if it is about the Baltics, and security[group] by 1 if it is about the Baltics and about security. Only those security counts per group go to the detector and to stream = batch.

The close rule (complete): both feeds' done markers have arrived and for each feed, the number of distinct keys received is at least the number announced. The second half matters: a marker can arrive while some of its file's articles were lost; the slot then waits for the producer's re-send rather than closing short.

The stuck rule (STUCK_SLOTS = 96): the oldest open slot is force-closed once a slot more than 96 slots (a day) newer is open. A lost done marker therefore stalls the monitor for at most a day, not forever. The test checks the boundary exactly: a slot exactly 96 slots later does not force the close, one 97 slots later does, and a mutation that sets STUCK_SLOTS = 95 must turn that test red.

Inside an open slot, self.ids[feed] is a set of (id, url) keys. A re-delivered message (at-least-once) hits the set and is ignored; two different articles sharing a GDELT id both count, because their urls differ (test_two_articles_sharing_a_gdelt_id_both_count). Before commit 8722648 this set held ids only, and the stream lost 18 % of translated security articles. Next stop: Spark's dropDuplicates (06 Batch layer).

Manual commits and at-least-once

The Kafka offset is the consumer's bookmark. The monitor commits it by hand, synchronously, only after a message closed at least one slot and no slot is left open (assembler.idle). By then the closed slots are written and the state is saved. So after any crash, Kafka re-delivers from the last commit, and what is re-read is either part of a slot that is already closed (dropped by ts <= last_closed) or part of an open slot that is rebuilt from scratch.

  1. Why does the producer archive the zip after publish returns, not before?

    Because the archive is the producer's only memory of what it has sent. Batch layer in depth

mirror, the mapper, the Spark job, the lake, the baseline and the scaling study

The batch layer turns 35.6 GiB of September zips into a lake of tens of MiB: mirror downloads them, Spark runs a MapReduce (one zip = one map task, counts summed by key) followed by Spark SQL, and writes Parquet. The same map function then runs in a plain Python Pool, so the scaling study can ask whether Spark earns its cost on one machine. It does not.

Step 0: mirror, the backfill

Before Spark can run, September must be on disk. mirror() lists every slot of the date range for both feeds, keeps only those not yet settled on disk, and downloads the rest with 12 threads: downloading is I/O bound, so threads overlap the waiting (the HTTP session's connection pool holds 16). Result: 5,760 zips (30 × 96 × 2), 0 missing, 35.6 GiB.

Trapmirror refuses the live window. Files from until on belong to the producer: archived by mirror, they would never reach Kafka, and the monitor would never count them. The CLI sets until = min(SINCE or a day ago, a day ago), and a mutation that removes the check must turn a test red.

mirror is safe to re-run: todo keeps only jobs where layout.has(feed, ts) is false, every file is written with write_atomic, and the test calls it twice to prove the second run reports {"already there": 192} for one day. A failed download stops the run; running it again resumes. The same skip-if-done rule runs bench.run_all below and every vm.sh step.

The Spark job, as a picture

The map step, with a combiner

A GKG zip cannot be split: you need the whole file to decompress it. So the unit of map work is one zip, read whole by binaryFiles. map_file parses every row with the same article.parse the speed layer uses, and emits two kinds of records:

  • ("article", row) for each relevant article (about a Baltic country, or from a Baltic outlet). Everything else is not kept as a row.
  • ("count", (key, (rows, about))), but only after the loop: the mapper has already summed its file's rows per (day, group, domain) in two Counters. That local pre-aggregation is a combiner: the shuffle moves thousands of counts instead of the ~350k rows a day (the independent collector counted 352,094 rows on 30 September).

Silver and gold: what the lake holds

The lake is small on purpose: only relevant articles become rows (110,221 relevant against 9,081,950 rows in the independent collector's 30 days), and everything else survives as per-domain counts in domain_day. That is enough for H1 (a share needs only counts) and keeps the AI step and the hypotheses fast on one machine.

The baseline: the same map in a Python Pool

To ask "does Spark earn its overhead?", you need the same work done without Spark. baseline.py runs the very same mapper.map_file in a multiprocessing.Pool; the parent process does the reduce (merging counts) and the de-duplication (a set of keys) that Spark does in SQL.

Spark and the Pool share mapper.map_file, so a speed difference is the engine's, not the code's. test_spark_and_the_baseline_agree_and_the_lake_is_written checks they also agree on files, rows and relevant, and test_baseline_is_the_same_whatever_the_number_of_processes checks Pool(1) = Pool(2).

bench.py: the study design

Three design choices make the numbers trustworthy:

  • Repeats and the median. Each configuration runs 3 times; the report quotes the median and the figure shows the range.
  • A shuffled, reproducible order (random.Random(1)): warm-up or page-cache effects cannot systematically favour one configuration, and a re-run gets the same order.
  • A fresh process per run (a fresh JVM for Spark), started as baltic measure, which counts instead of writing. A run whose result file exists is skipped, and a configuration with more workers than CPUs is skipped, so the study is resumable across reboots.

Worked example: speed-up and efficiency (report.scaling): speed-up(n) = median(1 thread) / median(n threads); efficiency(n) = speed-up(n) / n, where 1 is ideal.

  1. 4 threads: 806.0 / 234.0 = 3.44; 3.44 / 4 = 0.86. Close to linear.
  2. 8 threads: 806.0 / 285.2 = 2.83; 2.83 / 8 = 0.35. Slower than 4 threads: the 8 vCPUs are 4 physical cores with hyper-threads, and each task's Python worker competes with the JVM. You did not run an experiment that isolates that cause; say "most likely".
  3. Spark vs Pool at 7 days: 285.2 s vs 106.7 s. The rule: Spark "beats" the Pool only if its median is below the Pool's fastest repeat; spark_beats_pool is false.
  4. Data size: 30 days take 722.7 / 285.2 = 2.5× as long as 7 days for 30 / 7 = 4.3× the data: fixed costs (JVM start, Python↔JVM serialisation) dominate small inputs.
TrapDo not say "Spark is slow". On one node, its fixed costs (JVM start, moving every record between the JVM and the Python worker) are not paid back at 35.6 GiB. Its value here is the programming model and the unchanged path to a cluster (FW2, Dataproc Serverless). "Spark scales out" is an argument you have not measured.

AI matcher

the embedder service, match.py, and how H3 was judged

For every Russian/Belarusian article about the Baltics, find the Baltic article telling the same story within ±48 hours, once by meaning (multilingual sentence embeddings) and once by shared rare names, then judge both on a blind sheet at equal coverage. The AI is only interesting because it is measured against something.

The embedder: a model behind a private endpoint

Intuition first: a sentence embedding model reads a headline in any of 50+ languages and returns a point in a 384-dimensional space, placed so that headlines that mean the same thing land close together, even when one is Russian and the other Lithuanian. "Close" is measured by the cosine of the angle between two vectors: 1 means the same direction, 0 means unrelated.

Your model is paraphrase-multilingual-MiniLM-L12-v2. You chose it over LaBSE and E5 for size and CPU speed: 384 dimensions, 50+ languages including lt, lv, et and ru, small enough for a CPU container. You did not compare their accuracy, so never say "MiniLM is the best model".

The service is 41 lines of FastAPI. Read the whole endpoint: it encodes, normalises, and reports the model, the dimension and how long it took.

The client side sends at most 256 headlines per request and asks for a fresh ID token for every batch (Cloud Run tokens expire after an hour), always in the Authorization header, never in a URL:

Inference here is one bursty run (embed every distinct headline once, then stop), so the model runs on Cloud Run with --min-instances=0 --max-instances=2, 2 vCPU and 2 GiB: it costs nothing while idle and stays within the free tier. An always-on Vertex AI endpoint was estimated at ≈ $12 for the six days, billed while idle. The weights are baked into the image at build time, so a cold start only loads from disk.

Trap"Private" is not a network trick. The endpoint has a public URL; what makes it private is --no-allow-unauthenticated plus roles/run.invoker granted only to the VM identity and the operator. An unauthenticated call returns 403, which was checked live. The service's own identity, ccbd-embedder, has no roles at all.

match.py: two matchers over the same time window

  1. Load. From the September silver lake keep articles about the Baltics with a headline longer than 15 characters. Sources = ru_by; candidates = baltic and baltic_rus, sorted by time. Time t is minutes since the epoch.
  2. Embed each distinct headline once. match() builds a sorted set of all titles, sends it through Embedder.embed, and maps each title to its vector.
  3. Embedding matcher. For each source, two binary searches find the candidates between t − 2,880 and t + 2,880 minutes (48 h × 60). One matrix–vector product gives all their cosines at once; the highest wins.
  4. Entity baseline. Every person (p:) and organisation (o:) name is counted over sources and candidates. A name in 3 % or more of all those articles is ignored as too common (the code's example is "Putin"). A candidate inside the window gets one vote per shared rare name; the most-voted wins if it has at least 2.
  5. One row per source with both answers: emb_cos, emb_title, ent_shared, ent_title and the domains. Written to ai/pairs.parquet.

Why does searchsorted work? Because the candidates are sorted by time, the ones inside [t − window, t + window] form one contiguous slice dst[lo:hi]. If the sort were removed, the slice would be the wrong articles and nothing would crash: that silent failure is why tests/red_check.py has the mutation "candidates sorted by time".

TrapThe entity matcher is not "worse code". It is a conservative matcher: it answers only when two rare names are shared, so it matched only 6.9 % of the 3,613 ru_by articles, while 55.1 % had an embedding candidate with cosine ≥ 0.7. Comparing all embedding answers with the entity matcher's few confident ones would be unfair to it. That is why H3 compares them at equal coverage.

Statistics & detector

cluster bootstrap, Wilson intervals, equivalence, robust z

Every verdict is an interval plus a rule. Differences between groups get a cluster bootstrap (resample whole outlets, because one outlet's articles are not independent); precisions get a Wilson interval; "the same" needs an equivalence margin; and the spike detector uses median and MAD, because a mean is pulled by the very spikes it looks for.

The cluster bootstrap of a ratio difference

Intuition first. H1 asks whether ru_by's share of articles about the Baltics is larger than another group's: 1.11 % against 0.46 % for other foreign outlets, a difference of +0.65 percentage points. Is that real or luck? The bootstrap answers by asking: if September had come out slightly differently, how much would that difference wobble? It builds thousands of "alternative Septembers" by resampling the data you have, recomputes the difference each time, and reads the interval off the spread.

The crucial choice is what to resample. An outlet like ria.ru publishes many articles with one editorial line; they rise and fall together. If you resampled single articles, one huge outlet would look like thousands of independent witnesses and the interval would be falsely narrow. So the unit of resampling is the domain: each draw picks whole outlets, with replacement, keeping each outlet's articles together. This is a cluster bootstrap (the report cites Cameron, Gelbach & Miller 2008).

Read it slowly. The two arrays passed to stats.bootstrap are not the data but np.arange(len(na)) and np.arange(len(nb)): the cluster indices of each group. Every resample draws indices, and diff(i, j) sums the chosen clusters' numerators and denominators. That is how "resample domains" becomes four lines of code.

The same function serves both hypotheses because both are ratios of sums:

  • H1 share: numerator n_about, denominator n_rows, summed per domain from gold/domain_day.
  • H2 tone: numerator tone, denominator n = 1 per article, so Σ tone / Σ n is the mean tone per article, with the domain still the cluster. Tone is GDELT's % positive minus % negative words, so a difference is in tone points, never a ratio.
  1. H1 vs other, from the facts. ru_by 1.11 % minus other 0.46 % = +0.65 pp; the bootstrap interval is [0.45, 0.84]. The whole interval is above 0, so this half of the rule passes.
  2. H1 vs regional. 1.11 % minus 1.23 % = −0.12 pp, interval [−0.38, 0.11]. It contains 0, so "larger" is not shown. The rule needs both: H1 is rejected.
  3. Why clusters widen the interval, from your own test. test_clusters_widen_the_interval builds one outlet with 500 of 1,000 articles plus 20 outlets with 5 of 100 each, and compares it with 3,000 articles treated as independent. The clustered interval must come out wider: one dominant outlet is one witness, not 1,000.
TrapA bootstrap CI is not "the range where 95 % of articles lie". It is the uncertainty of one number (the difference of two group ratios) caused by which outlets happened to publish. Also: percentile method, 2,000 resamples, seed 0, so the same data always give the same interval (test_same_seed_same_interval).

Wilson intervals for precisions

A precision like 29/30 is a proportion from a small sample, close to 1. The textbook normal interval, p ± 1.96·√(p(1−p)/n), breaks exactly there: for 29/30 it gives 0.967 ± 0.064, an upper end of about 1.03 (arithmetic on the facts), a precision above 100 %. The Wilson score interval is built differently and always stays inside [0, 1], which is why stats.wilson uses it (Wilson 1927).

  2. The same numbers are in your results. The detector check: 7 of the 10 strongest alerts were real events, reported as 0.70 [0.40, 0.89], the test's interval rounded.

The spike detector: robust z with median and MAD

The question the detector asks every 15 minutes, for each group: is the number of security articles about the Baltics in the last hour far above what is usual for this hour? "Usual" is the median of the same hour on previous similar days (weekday vs weekend, because news volume halves at weekends), and "far" is measured in units of the MAD, the median absolute deviation.

Four details worth saying out loud:

  • Score before learning. The hour's value is appended to history only at minute 45, after it was scored, so a spike is never compared with itself.
  • The 1.4826 factor rescales the MAD so that, for normally distributed data, it estimates the standard deviation; the score then reads like a z-score.
  • The +1 in the denominator: sparse groups often have MAD = 0 (every past hour had the same count), and without it a single extra article would score infinity.
  • Rising edge, re-arm. A group alerts when it goes high and is not already in self.active; it re-arms when the score falls back. One event, one alert.
  1. Your test, exact. test_the_score_divides_by_scaled_mad_plus_one: eight days of zeros (median 0, MAD 0), then an hour of 2 articles per slot. Observed = 8, so the score is (8 − 0) / (1.4826 × 0 + 1) = 8.0. A detector with z = 8.0 alerts; with z = 8.01 it does not. The mutation "+ 0.5" instead of "+ 1.0" turns this test red.
  2. Illustration, not data. Same hour on five past weekdays: 3, 4, 4, 5, 6 articles; now 18. Median 4, absolute deviations 1, 0, 0, 1, 2, so MAD 1; robust z = (18 − 4) / (1.4826 + 1) ≈ 5.64 ≥ 4, and 18 ≥ 8: alert. A mean-based z gives (18 − 4.4) / 1.14 ≈ 11.9: also an alert.
  3. Illustration, not data: now one past day had a spike. History 3, 4, 4, 5, 40. Median still 4, MAD still 1, robust z still ≈ 5.64: alert. reconcile, stream = batch, the id bug, the 11 incident slots, tests, mutations, CI

A number is trusted only when two independent paths over the same input agree. Reconcile compares Spark with a separately written collector, day by day; stream = batch compares the live monitor with Spark, slot by slot. Two checks, two independent paths

Reconcile: Spark against an independent collector

In September a separate script counted, per day, every GKG row and every relevant article. Its counts are vendored in the package as analysis/reference_days.json (30 days; for 30 September: 352,094 rows, 4,132 relevant). reconcile() compares the lake with them:

  • Rows must be equal, exactly. domain_day counts every parsed row before any de-duplication, and gdelt.read_rows decodes and quotes like the reference collector, so the totals can match to the row.
  • Relevant articles within 0.5 %, because Spark de-duplicates by article key and the collector may not have done so identically.
  • A day the lake lacks fails (the loop runs over the reference's days, not the lake's), and comparing nothing is no pass: the CLI exits 0 only if at least one day was compared and all passed.

Result: 30 of 30 days; row counts equal on every day; relevant articles exact (worst day 0.0000 %). Before the id fix: 29 of 30, one day at 0.78 %.

Stream = batch: the speed layer against the batch layer

The monitor counts security articles about the Baltics per group and slot as messages arrive. Spark, run over the same raw files the producer archived (just etl-live), computes the same quantity in lake-live/gold/series_15m. stream_vs_batch() compares them for every slot from start to horizon:

  1. Keep one line per slot (drop_duplicates("slot", keep="last")): at-least-once delivery may write a slot twice after a crash; duplicates are counted, not failed.
  2. Expect every slot from start to horizon (gdelt.slots): a stalled or empty monitor fails as "missing", even if the slots it did write agree.
  3. Align both tables on slot × group, filling absent groups with 0, and mark a slot as differing if any group's count differs.
  4. ok only if there was something to expect, nothing differs and nothing is missing. The CLI exits 1 otherwise.

The check refuses to pass on absence: a missing slot fails on its own (test_stream_vs_batch_fails_on_a_missing_slot_alone), a stalled or empty monitor fails, and an empty window is not "ok". A system that silently stopped would otherwise look perfectly consistent, because the few slots it wrote would all agree.

Stream = batch is possible only because both paths share the slot key: the monitor writes one line per closed slot ("slot": ts) and Spark's series_15m groups by the same ts, so the check is a join on that key, not a judgement. It also requires every slot from start to horizon (gdelt.slots(start, horizon)), so a monitor that stalled in time order fails it.

up.sh, step by step

The constraint that shaped it: the GCP project was shared. You could not change anything project-wide (for example enabling the Dataproc API), so every resource is named ccbd-*, labelled purpose=ccbd-coursework, and created only if it does not exist yet. Running it again ships the current commit and the current startup script and changes nothing else. All names come from variables ($PROJECT, $BUCKET, $REGION = europe-north1); none is hard-coded.

  1. Storage. A bucket with uniform bucket-level access and public access prevention, labelled, with a lifecycle rule that deletes raw/ objects after 30 days.
  2. Identities. ccbd-vm gets roles/storage.objectAdmin on this bucket only; ccbd-embedder gets no roles. The binding is retried 5 times with 15 s pauses because a new service account takes a while to become visible to IAM.
  3. Model image. An Artifact Registry repository ccbd, then Cloud Build builds ai/embedder as embedder:v2, with its source staging and logs kept in our bucket, not the shared project's default buckets.
  4. Private Cloud Run. --no-allow-unauthenticated, 2 vCPU, 2 GiB, concurrency 4, 0 to 2 instances, 300 s timeout; run.invoker for the VM identity and, if set, the operator.
  5. Network. Own VPC ccbd-net, subnet 10.90.0.0/24, and one firewall rule: tcp:22 only from Identity-Aware Proxy's range 35.235.240.0/20.
  6. Code. git archive HEAD as a tarball to gs://<bucket>/code/baltic.tgz: the VM pulls exactly this commit on every boot.
  7. VM. If it exists, only its metadata and startup script are updated. Otherwise it is created: e2-standard-8, Debian 12, pd-balanced 80 GB, Shielded secure boot, OS Login, its own service account, a termination time of 2026-10-08 with action STOP, and vm.sh as the startup script.
Trapup.sh starts with set -euo pipefail and wraps every call as exists … || g … create …. "Idempotent" means: the second run finds everything, creates nothing, and only re-ships the code and the startup script. It does not mean the VM is rebuilt; an existing VM keeps its disk and its data.

vm.sh: what the VM does on every boot

The VM runs vm.sh as root on every boot, not just the first. That is the design that makes reboots, the stop at the self-stop time and the resize harmless: each step checks for its own output and skips itself, so a boot continues where the last one stopped. Its log goes to /var/log/ccbd.log and is copied to the bucket every 5 minutes.

The guards to know by heart: [ -f /swapfile ], command -v docker, command -v just, [ ! -d data/raw ] (restore only on a new disk), mirror skips files already on disk, [ -f data/lake/gold/series_15m/_SUCCESS ] (Spark writes _SUCCESS on commit, and series_15m is written last), seed never overwrites a live state, [ -f data/ai/pairs.parquet ], [ -f data/ai/labels_pairs.csv ], [ -f data/bench/.done ] and the benchmark skips runs whose result file exists. Network steps go through retry: five attempts with growing pauses.

Everything here is "safe to run again": up.sh creates only what is missing; every vm.sh step tests for its own output; mirror, seed and bench skip finished work; and layout.write_atomic writes through a temporary file and a rename, so a crash never leaves a half file that the next boot would mistake for finished. The resize boot proved it: it finished in 8 minutes and the stream resumed.

Scaling: why 8 threads lose to 4, and Spark to a Pool

  1. Speed-up at 4 threads: 806.0 ÷ 234.0 = 3.44; efficiency 3.44 ÷ 4 = 0.86. Near-linear: the work parallelises well.
  2. At 8 threads: 806.0 ÷ 285.2 = 2.83, efficiency 2.83 ÷ 8 = 0.35: slower than 4. An e2-standard-8's 8 vCPUs are hardware threads on 4 physical cores, and each Spark task also runs a Python worker beside the JVM, so 8 threads most likely compete for 4 cores. You did not run an experiment that isolates that cause: say "most likely".
  3. Spark vs Pool(8): 285.2 s vs 106.7 s on 7 days; 722.7 vs 518.7 on 30. Spark's fixed costs (JVM start, moving every record between the JVM and Python) are not paid back by 35.6 GiB on one node. With one worker the two are close (806.0 vs 723.2).
  4. Data size: 30 days take 722.7 ÷ 285.2 ≈ 2.5× as long as 7 days for 30 ÷ 7 ≈ 4.3× the data: fixed costs dominate small inputs.

The scaling study is a right-sizing result: the useful parallelism of this VM is 4, and on one node a plain process pool is enough. That is also why the VM was resized to e2-standard-2 after the batch work. Spark's value here is the programming model and an unchanged path to a cluster (FW2): an argument, not a measurement.
