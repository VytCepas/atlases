Networks

Tinklai · how two machines find and talk to each other
The idea

A message needs a name (DNS turns it into an IP), an address (IP, hierarchical so routers can route it), a door (the port), and a delivery promise (TCP reliable, UDP fast). The OSI layers hide all of this from the app developer.

Three identifiers, and only one is flat

Examplemano.vilniustech.lt158.129.192.195 · IPv6 2001:0db8:…:733458:A4:C6:9B:3D:21
Structurehierarchical, readable, any lengthhierarchical, 32 bit (v4) / 128 bit (v6)flat (not hierarchical), 48 bit
Who uses itpeoplerouters, to cross networksswitches, inside one network
TrapIPv6 uses colons like a MAC address. Count the groups: 8 groups of 4 hex = IPv6 (hierarchical); 6 pairs of hex = MAC (flat).

DNS: how a name becomes an IP

Ports: the door number on the machine

One IP, many programs. IP:port (a socket) picks the program: 192.168.1.10:443.

  • Slides: 80 web, 21 FTP, 25 SMTP mail. Also know 443 HTTPS, 22 SSH, 53 DNS. Well-known range 0–1023.
  • One program may use several ports (a web server on 80 and 443). Two programs cannot listen on the same port/protocol at once.
  • Any port can go in a URL: http://example.com:8080, so HTTP is not tied to 80.

Why layers help (a quiz question): app developers can ignore the transmission medium; changing one layer leaves the others working; each problem is solved separately, so less complexity; standard interfaces let different vendors' devices interoperate; new protocols slot in easily.

Distributed systems

Paskirstytos sistemos · many computers acting as one
The idea

Independent computers (no shared memory, clock or OS) cooperate over a network and look like one system. You gain scale, low latency and availability; you pay with partial failures, delays and consistency problems.

Flynn's taxonomy: count the streams

Why distribute at all: scalability, collaboration, low latency, mobility, high availability and fault tolerance, pay per use, delegated operations. One Google query touches about 1,000 computers and answers in 0.2 s.

Caching: keep a copy close to whoever asks again

CDN (Akamai, Cloudflare, Amazon CloudFront): serves from the nearest node. Uses: caching, shorter routes, security (DDoS protection), analytics. It analyses topology, monitors load, predicts demand, balances traffic. Results: faster loads, less origin load, failover, lower traffic cost. It does not lock a site to one country.

When caching hurtsFast-changing data goes stale; personal or exact values (balances, stock levels) must not be shared; invalidation can be harder than recomputing.

Availability: the arithmetic the exam asks for

all required (series)P(works) = (1 − p₁)(1 − p₂)…(1 − pₙ)any 1 of N (redundant)P(fails) = p₁ · p₂ · … · pₙ (= pᴺ if equal)whole systemcollapse each group to one block, then multiply the blocks' P(works)

Quiz question 9, drawn. R = reliable node (fails 0.5%), L = less reliable (fails 5%).

Lecture discussion task, solvedRequest goes to 1 of 2 servers → one server → 3 servers doing different work (all needed) → final node; each 1% unavailable. Works = (1 − 0.01²) × 0.99 × 0.99³ × 0.99 = 0.9999 × 0.99⁵ = 0.9509, about 95.1% available.

What goes wrong, and the vocabulary for it

Four challenges

  • Concurrency: simultaneous requests need locks; locks cost speed; replicas must apply operations in the same order.
  • Latency: messages take unknown time.
  • Partial failure: no global state; nobody knows exactly what failed.
  • Security.

Three network timing models

  • Synchronous: bound T known, so "dead" vs "slow" can be told apart.
  • Partially synchronous: T exists but unknown.
  • Asynchronous: no bound (the Internet). A slow message looks lost, retries cause duplicates, order can break.
  • Fail-stop: component halts (detected by time-out). Fail-restart: comes back, possibly with stale state.
  • State = info that cannot be rebuilt. Copy = backup against disaster. Cache = nearby copy for speed (may go stale; write-through).
  • Core principles: divide and conquer (→ MapReduce in 07), replication, quorum / consensus.

Cloud computing principles

Debesų kompiuterijos principai · distributed systems, rented by the hour
The idea

Computing becomes a utility: on-demand, elastic, metered (NIST 2011). The service model decides how much you still manage. Scaling out only works if the app is split into stateless pieces and the data is sharded.

NIST: 5 characteristics3 service models4 deployment models
on-demand self-service · broad network access · resource pooling · rapid elasticity · measured serviceIaaS · PaaS · SaaSpublic · private · hybrid · community

Timeline: 1960 McCarthy predicts "computing as a utility"; 1999 Salesforce (SaaS); 2006 AWS EC2 is the practical start; 2010 Armbrust et al.; 2011 NIST SP 800-145. Key property today: scalability.

Who manages which layer

Adding servers is not enough: the database lock

Real systems from the slides. Amazon: route users to the nearest server, split requests into microservices, parallel databases, multi-tier design, predict the next click. Facebook photos are written once and read many times, so they are cached at every layer:

Monolith → microservices (this is also lab task 1)

  • Quiz-tested properties: different technology per service is fine; small, independently deployed and horizontally scaled; own database where possible; usually Docker + Kubernetes. Not vertical scaling, not one server with identical config.
  • Stateless service: receive → process → return, keep nothing between requests. Persistent data goes to an external DB or file system (variables during a request are fine). Context travels in cookies, RPC/gRPC payloads or message queues.
  • Stateful: keeps sessions/history in itself: chat server, DBMS tracking transactions, service with sessions in RAM. E-store exercise: image resizing is stateless. The lecturer's rule: "it depends on how the service performs the action, not what it is responsible for". Recommendations are stateless if based only on the current request, stateful if they need your last clicks; the cart and purchase history can be served by a stateless service that reads and writes a database keyed by user ID.

End-to-end example from the slides: a media service

Message queues: decouple who sends from who processes

Scaling options (no single best): one multithreaded program; N single-threaded copies in VMs; N processes without virtualisation; N processes in containers. Music-service example: one container per user instead of one thread per user. Cloud designs use more total resources (duplication, coordination) to give the user a faster result.

Name the stages of the AI asset lifecycle and say how it loops.

When is a ready AI-as-a-Service solution better than building your own?

Virtual environments, VMs, containers

Virtuali aplinka, VM ir konteineriai · how much you isolate
The idea

Three levels of isolation. A venv isolates Python libraries. A VM isolates a whole operating system on a hypervisor. A container isolates a process with its libraries but shares the host's kernel, which makes it light and fast. Kubernetes runs many containers for you.

venv / condaVirtual machineContainer
IsolatesPython packages per projectwhole guest OSprocess + filesystem + libs
Good fordifferent library versions, no conflicts, easy sharing (requirements.txt)testing, running risky files, several OSes, cloud servers, learningportable deploys, CI/CD, microservices, one service per container
Weak atnot isolated from OS; system tools (gcc, libxml2) still yours; must activateRAM/CPU/disk heavy, slower than nativepartial isolation, harder security, networking to learn
Quiz trapsVMs are not lighter. Containers do not need more RAM and are not Linux-only. A venv does not need Docker, does not isolate the OS, does not install system tools, and is not only for big projects.

source my_environment/bin/activate      # Windows: my_environment\Scripts\activate
pip freeze > requirements.txt          # share;  pip install -r requirements.txt
conda env export > environment.yml     # share;  conda env create -f environment.yml
Type 1 · bare-metal hypervisorRuns directly on hardware. Servers and clouds. VMware ESXi, Hyper-V (server), Xen, KVM. Faster, more stable.
Type 2 · hosted hypervisorAn app on your existing OS. Testing and learning. VirtualBox, VMware Workstation/Fusion, Parallels. Easy to install.

Docker in one screen

Dockerfile (recipe) → docker build → image (template, shareable via Docker Hub) → docker run → container (running copy).

FROM python:3.12-slim            # base image
WORKDIR /app
COPY . .
RUN pip install flask            # dependencies baked into the image
CMD ["python", "app.py"]         # what runs when the container starts

docker build -t my-app .         docker run -p 5000:5000 my-app   # host:container port
docker ps -a   docker logs <id>   docker exec -it <id> bash   docker stop <id>   docker system prune -a

Kubernetes: who keeps the containers alive

Kubernetes: open source, created by Google, now run by the CNCF. Runs on AWS EKS, Azure AKS, Google GKE or your own servers. Downsides: complex, steep learning curve, uses resources itself, needs add-ons (Helm, Prometheus, Istio).

Edge and fog computing

Krašto kompiuterija · move the computing to the data
The idea

Distance costs time. Process data on or near the device (edge), in a regional middle tier (fog), and send only what is needed to the cloud. That cuts latency and network load and protects privacy, at the price of managing many small, weak, exposed nodes.

Latency ladder: why distance matters

Ways to cut latency in AI web systems: shrink the model (quantisation, pruning, distillation), send only essential data (a crop, not the whole image), faster hardware (GPU, TPU, FPGA), answer asynchronously (rough result first), pipelining and batching, load balancing, CDN for requests and model weights, caching answers, Edge AI, faster protocols (HTTP/3, QUIC).

Edge, fog, cloud

Edge gains

  • lower latency
  • less network load
  • privacy: video and biometrics stay local
  • keeps working if the cloud link drops

Edge costs

  • expensive to deploy and maintain
  • many nodes to update and monitor
  • weak CPU, memory, storage
  • no standards across vendors
  • nodes die with power or network
  • more places to attack

Five ways to train a model on arriving data

Streaming vs batch architectures: Lambda vs Kappa

Streaming: continuous, event-driven, item by item or in micro-batches, latency-critical (Flink, Kafka Streams, Spark Structured Streaming; on devices TensorFlow Lite, ONNX Runtime). Users: Uber (price spikes), LinkedIn (event digests), Netflix (personalisation), TripAdvisor (profit, fraud). Batch: collect for a time window (5 min) or a count (1,000 records), then process; cheaper, but decisions come late, so it is wrong for critical real-time control.

Big data and MapReduce

BigData ir MapReduce · divide and conquer, applied to data
The idea

When data is too big for one machine, cut it into shards, run the same map function on every shard in parallel to emit (key, value) pairs, let the framework group by key, then reduce each group to one result. The framework handles distribution, retries and failures.

5 VMeaningExample
VolumeTB, PB and beyondyears of click logs

Varietystructured, semi-structured, unstructuredtables · JSON/XML/logs · text, images, video
Veracityquality and reliabilityduplicates, errors
Valuebenefit you can extractforecasts, insights, automation

"Big" has no fixed size: it depends on the era and the organisation (8V and more exist). Tools: processing Hadoop, Spark (in-memory, the de facto standard), Flink, Storm, Kafka Streams · storage HDFS, MongoDB, Cassandra, HBase, Redis, S3, BigQuery · integration Kafka, NiFi, Airflow · ML Spark MLlib, TensorFlow, PyTorch, pandas, Dask · dashboards Tableau, Power BI, Grafana, Kibana.

MapReduce, step by step, on real words

  • Google, 2004. Runs on a distributed file system (GFS chunkservers); input/output usually in GFS or BigTable.
  • The framework hides: parallelism, distributing data to workers, load balancing, retries on failure. Implementations: Hadoop MapReduce, Amazon EMR, Azure HDInsight, Google Cloud MapReduce.
  • Jobs are usually Java; Hadoop Streaming runs Python. Test locally: cat data | ./mapper.py | sort -k1,1 | ./reducer.py. The reducer works because input arrives sorted, so equal keys are adjacent.
  • MapReduce does not guarantee speed: the resource-saving design adds disk work.

Joint schema (slide 16): the client forks the master; the master assigns M map work items (one per input shard) and R reduce work items; map workers write intermediate files (IF), reduce workers read them across the network after the shuffle, and each reduce worker writes one of R output files.

Spark, Hive, BSP, Bigtable, Spanner

Spark ir kitos technologijos · lecture exists in Lithuanian only
The idea

MapReduce writes to disk between every step and makes iterative jobs painful. Hive puts SQL on top of it; Spark keeps data in memory and runs whole DAGs of steps; Bigtable and Spanner are Google's answers for storing the data at that scale.

Why Spark is faster than MapReduce

Classic questionreduceByKey is a transformation, reduce is an action. Anything that returns a new RDD is lazy; anything that returns a value or writes output triggers the job. groupByKey ships every value across the network; reduceByKey pre-combines on each node, so it is usually faster.

Spark ecosystem (slide 18): Spark SQL, Spark Streaming, MLlib (machine learning) and GraphX (graphs) on top of the Spark Core API, usable from R, Python, Scala, Java and SQL.

  • Shared variables: broadcast (read-only copy cached on every node) and accumulators (counters and sums; only the driver can read them).
  • Execution: the cluster manager splits a job into tasks and sends them to executors (JVM processes) on workers, as close to the data as possible. RDDs come from files (HDFS, S3, HBase, Cassandra), streams (Spark Streaming, sliding windows) or other RDDs.

Apache Hive: SQL that becomes MapReduce

HiveQL query → Driver opens a session → Compiler parses it, asks the Metastore for table metadata, builds a DAG plan (optimiser) → Execution engine submits MapReduce jobs → results read from HDFS → back to the UI (web, CLI, JDBC/ODBC). Tables are HDFS files plus metadata; user-defined functions extend it.

Flaws in the provided code

  • The server evaluates on every upload, then clears clients_data, so each decision sees one client, never the whole group: the 80% rule cannot work.
  • No region, although working hours are defined per region.
  • The client writes every key pressed to a plain-text file in keystroke_logs/, passwords included, so the edge privacy benefit is lost on the PC itself.

4 · MapReduce run on the sample data

Data: Date;User ID;Order ID;Product ID;Quantity;Price. Questions 2 and 3 need two chained jobs because the condition is on an aggregate (see the key-design table).

from itertools import groupby

def run(lines, mapper, reducer):                        # map → shuffle/sort → reduce
    pairs = sorted(kv for line in lines for kv in mapper(line))
    return [out for k, grp in groupby(pairs, key=lambda kv: kv[0])
            for out in reducer(k, [v for _, v in grp])]

def parse(line):
    d, u, o, p, q, price = line.strip().split(";")[:6]
    return d, u, o, p, int(q), float(price)

# 1. daily sales = SUM(qty*price)
m1 = lambda l: [(parse(l)[0], parse(l)[4] * parse(l)[5])]
r1 = lambda day, vals: [(day, round(sum(vals), 2))]

# 2. orders per day with SUM(qty) > 3
m2a = lambda l: [((parse(l)[0], parse(l)[2]), parse(l)[4])]           # key (day, order)
r2a = lambda key, vals: [(key, sum(vals))]
m2b = lambda rec: [(rec[0][0], 1 if rec[1] > 3 else 0)]                # key day
r2b = lambda day, vals: [(day, sum(vals))]

# 3. user with most orders + total quantity
m3a = lambda l: [(parse(l)[1], (parse(l)[2], parse(l)[4]))]            # key user
r3a = lambda u, vals: [(u, (len({o for o, _ in vals}), sum(q for _, q in vals)))]
m3b = lambda rec: [("max", rec)]                                        # one key → one reducer
r3b = lambda _, vals: [max(vals, key=lambda uv: uv[1][0])]

lines = open("duom.txt").read().splitlines()
print(run(lines, m1, r1))
print(run(run(lines, m2a, r2a), m2b, r2b))
print(run(run(lines, m3a, r3a), m3b, r3b))

from pyspark.sql import SparkSession, functions as F

  • edge (device) vs fog (regional) vs cloud (central)

Three moves for the exam hour

  1. Reliability question: draw the chain, mark each stage "any 1 of N" or "all of N", collapse groups, multiply.
  2. MapReduce question: ask "one result per what?". That is the key; the smallest summable thing is the value.
  3. Matching question: look for the lecture's exact phrase ("last N points", "without losing previous knowledge", "two processing layers").

60 minutes for 10 points is about 5 minutes per point. Do matching questions first; they are fastest.
