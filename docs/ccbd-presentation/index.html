The question

Three hypotheses, rules fixed before the tests

Do Russian and Belarusian outlets cover the Baltic states differently from the rest of the press?

H1attention

ru_by give the Baltics a larger share of their output than other foreign outlets and than the neighbours

Accepted when: both CIs above 0
H2tone

(a) non-security stories: ru_by tone is lower
(b) security stories: the same, within ±0.5

(a) both CIs below 0 · (b) both CIs inside ±0.5
H3AI matching

Multilingual embeddings find "the same story" more precisely than shared names

At equal coverage: embedding lower bound > names upper bound
Data: GDELT GKG 2.1, English + ~65 machine-translated languages, a file per feed every 15 min Groups by outlet: ru_by (.ru .by + RT, TASS, Sputnik, …) · regional (.pl .fi .se .no .dk .de) · other · baltic (.lt .lv .ee) · baltic_rus Statistics: domain-clustered bootstrap, 2,000 resamples, 95 % CI

Say: Russian and Belarusian media are often said to over-cover the Baltics and to cover them negatively. I turned that into testable hypotheses and wrote each decision rule down before running the test.

H1 attention: a larger share than both other foreign outlets and the Baltics' own neighbours; both CIs above 0. H2 tone: (a) more negative outside security, (b) the same within ±0.5 on security. H3 is the AI part: embeddings against shared names, at equal coverage.

Groups are assigned by outlet domain. CIs from a bootstrap that resamples whole domains, 2,000 resamples. If asked: an exploratory pass (counts and overall tone, no CIs) came before the rules, and the code says so.

Architecture

Lambda on Google Cloud

container on the VM Kafka private bucket private Cloud Run
Lambda, not Kappa: history lives in the bucket, Kafka stays small (14 days). Price: two code paths, so one shared parser and a stream = batch check on every boot. 1private bucket, uniform access + public access prevention 2no Kafka host port, SSH only through IAP 3private Cloud Run, identity with no roles

Step 0 (GDELT only): the source: two GDELT feeds, a new file every 15 minutes.

→ Speed layer: the producer polls GDELT and publishes every article to Kafka, topic gkg.raw. The monitor reads Kafka, closes 15-minute slots, runs the spike detector, writes slots and alerts to the bucket.

→ Batch layer: the mirror backfilled September into raw/. The dashed arrow: the producer archives each zip into raw/ only after Kafka acknowledged every message, so a crash re-publishes instead of losing data. Spark turns raw/ into a Parquet lake, silver articles and gold aggregates.

→ Serving layer: the matcher sends headlines to a private Cloud Run embedder; the report reads the lake, the monitor output and the pairs, and runs the checks.

→ Why Lambda: Kappa would put the whole history into one unreplicated broker. Lambda keeps it in the cheap, durable bucket. The price is two code paths; one shared parser (article.py) and the stream = batch check pay it. Security in one line each (numbers on the drawing).

KAFKA_LOG_DIRSthe log lives in a named volume (commit e2e93cc)

Spark (PySpark 4) · local[n]

one JVM, n worker threads: vertical scaling · shuffle.partitions = 4n
binaryFileswhole zips as input splits (a zip cannot be split)
flatMap(mapper.map_file)map + per-file partial counts (a combiner)
reduceByKeycounts summed per (day, group, domain)
dropDuplicates(KEY)de-duplicate by article key (id, url)
write.parquetthe action: lazy evaluation runs the DAG here

Kafka: KRaft, one broker that is also the controller. One partition on purpose: Kafka orders only within a partition, and the monitor's close rule needs the global time order. At about 4 messages a second one partition is ample. Producer: acks=all plus idempotence, zstd, linger 50 ms. Consumer: auto-commit off, commits by hand after its state is saved and no slot is half-read, so a kill costs time, not data. 14 days of retention. The log dir was found outside its volume by inspection and fixed (e2e93cc).

Spark: local mode, one JVM with n threads, vertical scaling. MapReduce then SQL: binaryFiles reads whole zips; flatMap runs the shared parser and emits articles plus per-file counts, the combiner; reduceByKey sums counts per day, group, domain; Spark SQL de-duplicates on (id, url); the Parquet write is the action that runs the lazy DAG. shuffle.partitions = 4n instead of 200.

Scaling study · e2-standard-8, median of 3 runs, shuffled order

Scaling: the honest result

8 threads are slower than 4234.0 s → 285.2 s

8 vCPUs are 4 physical cores with hyper-threads; Python workers compete with the JVM

Spark loses to a Python pool on one node285.2 s vs 106.7 s

7 days. Fixed cost (JVM start, Python↔JVM serialisation) is not paid back at 35 GiB

Say: Three experiments on an e2-standard-8, median of 3 runs in shuffled order. E1, data size, Spark local[8]: 58.6 s for one day, 285.2 for seven, 722.7 for thirty. E2, cores on seven days: 806.0, 412.4, 234.0, 285.2 s for 1, 2, 4, 8 threads; speed-up 1.95, 3.44, then 2.83.

Two honest findings. 8 threads are slower than 4: 4 physical cores with hyper-threads, and the Python workers compete with the JVM. That is my explanation; I did not isolate it. And E3: the same map function in a plain multiprocessing pool wins on one machine, 106.7 s against 285.2. Spark's value here is the programming model and the path to a cluster (FW2), not single-node speed.

Say: The AI component answers H3. For each ru_by article about the Baltics, the matcher sends headlines to a private Cloud Run service running a multilingual MiniLM model, and takes the most similar Baltic headline within 48 hours. The baseline is what you would do without a model: the article sharing the most rare names.

Fair comparison: equal coverage. The embedding arm takes exactly as many top pairs as the names baseline matched. "Same story?": embeddings 29 of 30, 0.97, interval 0.83 to 0.99. Names 8 of 30, 0.27, interval 0.14 to 0.44. Lower bound above upper bound: H3 shown.

Backup B2 · Kafka

Why one partition, and what does at-least-once mean?

  • Kafka orders messages only within a partition; the monitor closes 15-min slots in time order. ~4 msg/s on average: one partition is ample
  • Never lost: acks=all + idempotence; a zip is archived only after every ack; offsets committed by hand after state is saved
  • May repeat: duplicates dropped by key (id, url); re-read messages of closed slots ignored. Replay of 514,959 messages closed 150 slots, each once; 322 live slots by Oct 4, each exactly once
  • Not exactly-once: a crash between writing a slot and saving state can write one slot line twice; the checks count it

Backup B11 · spike detector

Does the detector work?

  • Robust z-score (MAD) of each group's rolling-hour security count vs the same hour on similar days · backtest: 76 alerts in 2,880 slots
  • Blind check, same LLM annotator: 7/10 strongest alerts were real events (0.70 [0.40, 0.89]) vs 5/10 busy hours without an alert (0.50 [0.24, 0.76])
